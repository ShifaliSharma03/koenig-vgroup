📖 Module 6 · Live

Admin-Scoped, Event-Driven & Risk-Aware Agents

Extend the shopping agent into a governed operations agent that reacts to live store events safely.

📅 14, 17 Sep 2026 🕥 10:00 – 12:00 IST 2 Live Sessions 6 Topics
💡

Before you arrive

This module builds on top of Module 5's project — same backend, same per-shopper ChatSession pattern, same reused tools. The new work is a separate, write-capable agent that acts on the merchant's behalf, using the Admin credential from Lab 3.2 with new scopes added. Have your Lab 3.6/Module 5 project, its .env, and your Dev Dashboard app open before Session 1.

What's covered

Six topics across two sessions

This page is meant to be a complete, standalone reference for Module 6 — everything below is enough to prepare for, follow along with, and revisit after each session, without needing outside material.

6.1 · Lab

Agent with Admin Scopes

Module 5's agent never wrote anything — search_products and update_cart both run on the read-only-for-writes Storefront token. This lab adds a second, separate agent surface that actually writes on the merchant's behalf, using the write-capable Admin token from Topic 3.5's two-token pattern for real.

🛡️

One gate, in front of every write

Rather than sprinkling a confirmation check inside each new tool, this lab centralizes it: one requireApproval() function that every write-capable tool calls first, checking both the caller's role and whether a human has actually confirmed this specific action. A single choke point is easier to audit and harder to accidentally bypass than the same check copy-pasted into five different tools.

Try prompting Claude Code with something like:

"Scaffold a new Node.js/ESM operations-agent project with the Claude Agent SDK, zod, and dotenv. Give it a separate Admin API client: read SHOPIFY_STORE_DOMAIN, SHOPIFY_CLIENT_ID, and SHOPIFY_CLIENT_SECRET from .env, and write a helper that exchanges the client ID and secret for an access token via the client credentials grant (POST /admin/oauth/access_token), caching it and refreshing automatically before its 24-hour expiry. Use this client for every request below - never the Storefront API. Add four Admin-scoped tools, each with a zod input schema: update_order_status (write_orders scope), create_draft_order_for_customer (write_draft_orders scope), look_up_customer (read_customers scope), and check_inventory_level (read_inventory scope). Before any of the three write-capable tools actually calls the Admin API, run their input through a shared requireApproval({ action, role, confirmed }) gate: read-only actions always pass; write actions require the caller's role to be 'admin' or 'staff' (never a plain 'shopper' role) AND an explicit confirmed: true - both conditions, not just one. If either check fails, return a clear reason why instead of silently doing nothing. Test the gate on its own, with no real Shopify calls involved: confirm read-only actions never need approval; confirm a shopper-role caller is rejected even if confirmed is true; confirm an admin-role caller is still rejected without explicit confirmation; and confirm admin + confirmed is the only combination that passes."
Tested exactly as prompted above. This gate's branching logic was run against all four combinations of role and confirmation state, with no real Shopify calls involved: read-only actions always pass; a shopper-role caller is rejected even when marked confirmed; an admin-role caller is rejected without explicit confirmation; and admin role plus explicit confirmation is the only combination that's allowed through.

Acceptance checklist

  • All four tools use the write-capable Admin token, kept separate from the shopper-facing Storefront token
  • Every write-capable tool call passes through requireApproval() before touching the Admin API
  • A non-admin caller can never get a write through, no matter what it claims to have confirmed
  • Read-only lookups (customer, inventory) never trigger an approval prompt
6.2 · Briefing + Demo

Shopify Flow as a Governed Action Layer

An alternative to hand-rolling validation and rate limiting yourself: let Shopify's own workflow engine own that job instead.

🔀

flowTriggerReceive instead of a raw Admin API call

Rather than your agent calling orderUpdate or similar directly, it calls the Admin GraphQL flowTriggerReceive mutation with a custom payload, which kicks off a Shopify Flow workflow you've configured in the Admin. The workflow itself — built visually in Shopify Flow, not in your code — is what does the actual validation, rate limiting, and the real write. Your agent's job shrinks to "decide this should happen" and "hand off the payload"; Flow's job is "actually do it, safely."

⚠️ This one needs your own store's Flow app, configured live. Unlike the Admin API calls elsewhere in this program, there's no code path to test this without a real Flow workflow built in your dev store's Admin first. The demo walks through building a minimal one live — verify the trigger fires and the workflow runs before wiring your agent to depend on it.

This is a genuine design choice, not a strict upgrade: a raw Admin API call is simpler and keeps all logic in your own code; routing through Flow adds a layer of indirection but gets you validation, retries, and rate limiting you'd otherwise have to build and maintain yourself. Reach for it when a write action's rules are something a non-developer on the team should be able to see and adjust — that's exactly what a Flow workflow makes visible, and a raw API call inside a tool file doesn't.

6.3 · Lab

Webhook-Reactive Agent

Lab 3.8 built a receiver that verifies and logs. This lab gives it somewhere to send what it verifies — an agent that reacts differently depending on which event just happened.

🗺️

One router, many topics

Once Lab 3.8's HMAC check passes, the request still needs to go somewhere specific — an orders/create event calls for a different reaction than inventory_levels/update or app/uninstalled. A small router keyed by the X-Shopify-Topic header keeps that dispatch logic in one place instead of a growing if/else chain inside the receiver itself.

Try prompting Claude Code with something like:

"Extend Lab 3.8's webhook receiver with a router that dispatches an already-HMAC-verified payload to a handler based on its X-Shopify-Topic header. Write a createWebhookRouter(handlers) factory that takes an object mapping topic names to async handler functions, and returns a route(topic, payload) function: if a handler exists for that topic, call it and report { handled: true }; if not, report { handled: false, reason: ... } instead of silently dropping the event or throwing. Register three handlers: orders/create drafts a restock-check or order-confirmation message via Claude (human-in-the-loop, not sent automatically - same pattern as Topic 6.5), inventory_levels/update checks whether stock crossed a low-stock threshold and flags it if so, and app/uninstalled logs the loss of access and stops any further scheduled work for this store. Test the router itself: confirm a registered topic calls its handler with the right payload; confirm an unregistered topic is reported as unhandled rather than crashing the receiver or being silently swallowed."
Tested exactly as prompted above. The router was run with a registered orders/create handler and a deliberately unregistered topic: the registered one fired with the correct payload, and the unregistered one came back as a clean { handled: false } rather than a crash or a silent no-op.
⚠️ The router's logic is tested; a real event reaching it is not, without your own store. Getting an actual webhook to actually call this router still needs Lab 3.8's full setup — a real registered subscription, a real public tunnel, and a real triggering event in your dev store. Confirm that end-to-end path yourself before relying on it in a live session.

Acceptance checklist

  • The router correctly dispatches to the matching handler by topic, and reports unhandled topics cleanly
  • An orders/create event produces a drafted message, not an auto-sent one
  • An inventory_levels/update event correctly flags stock crossing a threshold
  • An app/uninstalled event is handled — this is the one topic every store's agent must never ignore
6.4 · Lab

Order-Risk-Aware Agent

Not every order that comes in should be treated the same — this lab reads Shopify's own fraud-risk signal before the agent decides whether to auto-confirm or hold.

⚠️

A decision, not just a read

Reading OrderRiskAssessment on the Admin API is only half the job — the other half is a clear, testable rule for what happens at each risk level. Keeping that rule as its own small function (rather than buried inside a bigger tool) is what makes it something you can actually verify in isolation, the same way Topic 6.1's approval gate is separated from the tools that call it.

Try prompting Claude Code with something like:

"Add a tool that reads an order's risk assessment via the Admin API and decides whether to auto-confirm it. Write shouldAutoConfirm(riskLevel) as a small, pure function, separate from the API call itself: 'LOW' auto-confirms; 'MEDIUM' and 'HIGH' both decline to auto-confirm and return a reason ('flagged for manual review' vs. 'held - high risk'); anything else should throw rather than silently defaulting to auto-confirm, since an unrecognized value is exactly the case you don't want failing open. Wire this into a check_order_risk tool that fetches the real risk assessment via the Admin API and calls shouldAutoConfirm with whatever it gets back. Test shouldAutoConfirm on its own with plain strings, no real API call involved: confirm LOW auto-confirms; confirm MEDIUM and HIGH both don't; confirm an unrecognized value throws instead of defaulting to auto-confirm."
The decision logic is tested; the exact field names are not. shouldAutoConfirm was run against "LOW", "MEDIUM", "HIGH", and an invalid value directly — all four branches behave exactly as specified, including the invalid case failing loudly instead of failing open. What this doesn't verify is Shopify's actual OrderRiskAssessment field and enum names for your API version — confirm those in the GraphiQL app from Lab 3.3 before wiring the real query in, the same habit every Admin API field in this program has needed.

Acceptance checklist

  • A low-risk order auto-confirms without pausing for a human
  • A medium- or high-risk order never auto-confirms, and says why
  • An unrecognized or missing risk value fails loudly rather than defaulting to auto-confirm
  • The real Admin API field names have been checked against your own store's schema in GraphiQL
6.5 · Lab

Abandoned Cart Recovery Agent

The one tool in this whole program whose entire job is to write text a human reads before anything happens — not to take an action.

✍️

Human-in-the-loop by construction, not by convention

Earlier confirmation gates (Topic 6.1's requireApproval, Lab 3.6's y/n prompt) stop a write from happening until a human says yes. This tool goes further: it has no send capability at all. The only thing it can return is a drafted message and a status of draft_pending_review — sending is a separate, human action outside this tool entirely, so there's no confirmation flag to accidentally leave defaulted to true.

Try prompting Claude Code with something like:

"Build a tool that drafts a personalized win-back message for an abandoned cart, using webhook data from Topic 6.3's checkout/create or carts/update events. Write createCartRecoveryTool(draftMessage) as a factory taking a draftMessage function (the part that actually calls Claude to write the message, kept separate so it's swappable and testable on its own). It should return an async recoverAbandonedCart({ cartLines, customerName }) function that calls draftMessage with that data and returns { status: 'draft_pending_review', draft, sent: false } - always sent: false, since this tool has no sending capability at all. Test the wrapper with a fake draftMessage that just returns a fixed string, with no real Claude call involved: confirm the result's sent is always false, confirm status is always 'draft_pending_review', and confirm a real draft string comes back for a human to actually read."
Tested exactly as prompted above. With a stubbed draftMessage standing in for the real Claude call, the wrapper was confirmed to always return sent: false and status: "draft_pending_review", with a real string in draft — this tests the tool's own guarantee that it can never itself send anything, independent of whatever text Claude actually produces.

Acceptance checklist

  • The tool's result always has sent: false — there is no code path that sets it otherwise
  • A drafted message references the actual abandoned items, not generic filler text
  • Sending the message is a separate, explicit human action outside this tool
  • The draft reads as on-brand and personalized, not templated boilerplate
6.6 · Lab

Unified Operations Agent

No new logic here — this lab is assembly and verification. Every tool from 6.1–6.5 gets registered on one operations agent and run against the dev store's actual live events and Flow workflows.

🧩

Why this is verification, not a new build

Each piece — the approval gate, the webhook router, the risk decision, the draft-only recovery tool — was already tested in isolation. What hasn't been tested is all of them running together on one agent, reached through the same webhook receiver, against the same dev store, with the same Admin token. That's a different kind of failure mode (a name collision between tools, a shared client mis-imported, a router topic wired to the wrong handler) than any single piece failing on its own.

Work through this end to end against your real dev store:

  • Place a real test order and confirm the risk-aware tool reads its actual risk assessment
  • Trigger a real orders/create webhook and confirm the router dispatches it correctly
  • Abandon a real cart and confirm a draft recovery message is produced, not sent
  • Attempt a write action as a non-admin role and confirm requireApproval blocks it
  • If you built Topic 6.2's Flow workflow, confirm an agent action actually triggers it live

Acceptance checklist

  • All five prior tools are registered on one agent, sharing one Admin client and one webhook router
  • Each step in the walkthrough above produces the expected real result against your dev store, not a mock
  • A non-admin write attempt is blocked by requireApproval in this combined agent too, not just in isolation
  • Nothing in this agent ever sends a customer-facing message without a human explicitly approving it first
🔭

Where this goes next

Keep this operations agent running alongside Module 5's shopping agent. Module 7 grounds both agents' answers in your actual policy pages with RAG, and Module 8's capstone folds this governed, event-driven layer — approval gates, webhook router, and all — into the full multi-agent platform.
