4.1 · Briefing

Model Context Protocol (MCP), Explained

Every custom tool built so far in this program has quietly been an MCP server. This topic makes that explicit before Topic 4.3 takes it further.

🔌

Why MCP exists

Before MCP, connecting an LLM to N different tools or data sources meant writing N different bespoke integrations, and every new client application had to redo that work again. MCP (Model Context Protocol) is Anthropic's open standard — open-sourced in November 2024 — for one common client-server protocol any LLM application can speak to any compliant tool/data server, so the integration gets written once.

🎁

You've already been using it

createSdkMcpServer() — used all the way back in Module 2's Lab 2.3, and in every Shopify tool since — builds a real MCP server. It's just run in-process, wired directly into query()'s mcpServers option, with no network hop and no other client able to reach it. Topic 4.3 takes that exact same tool logic and exposes it as a standalone server anything MCP-aware can connect to — the protocol underneath doesn't change, only its reach does.

🏗️

Architecture: host, client, server

A host (Claude Code, Claude Desktop, or your own agent) contains one or more clients, each holding a dedicated 1:1 connection to one server. A server exposes some mix of three primitives: tools (actions the model decides to invoke — everything built in this program so far), resources (data the host application controls access to), and prompts (reusable templates the user selects).

Two transports matter here: stdio, where the host launches the server as a local subprocess and talks over its stdin/stdout (what Claude Desktop uses for local servers), and Streamable HTTP, a real network endpoint any client can reach remotely — what Shopify's own MCP servers use, and what Topic 4.3's server uses too.

4.2 · Briefing + Demo

Shopify's Official MCP Servers

Shopify exposes several of its own MCP servers, no custom code required. This topic tours them and demos connecting to one directly from Claude Code.

🏪

Storefront MCP

Every Shopify store exposes a Storefront MCP endpoint, giving any MCP-aware client product search and cart/checkout capability against that store's real catalog — the same job as Module 5's hand-written search_products and update_cart tools, but with zero code and zero control over exactly what's exposed or how it behaves.

🧰

Customer Account MCP, Checkout MCP & the Dev MCP/AI Toolkit

Customer Account MCP and Checkout MCP extend the same idea to authenticated customer-account actions and checkout completion respectively — both newer and more limited in scope than Storefront MCP. Separately, the Dev MCP / AI Toolkit isn't shopper-facing at all: it's a developer-facing server that surfaces Shopify's own API docs and schemas, useful inside Claude Code itself while you're building the labs in this program.

Try prompting Claude Code with something like:

claude mcp add --transport http shopify-storefront https://your-store.myshopify.com/api/mcp

Then, in the same Claude Code session, ask it something like "search this store for snowboards" in plain language — no code, no .env, no tool you wrote yourself.

⚠️ Verify the exact endpoint and available tools against your own dev store first. Shopify's MCP surface is new and still evolving — confirm /api/mcp is live on your store and see what claude mcp list reports before relying on it in a live session, the same "test it live before trusting it" habit every Shopify API in this program has needed.

Why build your own at all, then?

  • Storefront MCP exposes what Shopify chose to expose — Module 5's confirmation gate on create_draft_order-style writes, or a cart tool that tracks state your way, isn't something you control there
  • It can't call your own Admin-scoped tools (order status lookups, discount logic) alongside the Storefront ones in a single coherent tool set
  • Topic 4.3 is what lets you keep everything built in Module 5 while still being reachable by any MCP client, not just your own agent.js
4.3 · Lab

Build a Custom Shopify MCP Server (Node.js)

Re-expose Module 5's tools as a standalone, standards-compliant MCP server any MCP-aware client can use — not just the query() call that owned them before.

🔀

A different SDK for a different job

createSdkMcpServer() from the Claude Agent SDK only ever runs in-process, wired straight into one query() call — that's why Module 5's tools couldn't be reached by anything else. This lab uses the official, LLM-agnostic Model Context Protocol SDK (@modelcontextprotocol/sdk) instead: it speaks the real MCP wire protocol over a real transport, so it can be reached by Claude Code, Claude Desktop, or any other compliant client — including, if you wanted, a completely different agent framework.

Step 1 — Install and write the server

npm install @modelcontextprotocol/sdk zod
mcpServer.js — same tool logic as Module 5, a different registration API
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js"; import { StreamableHTTPServerTransport } from "@modelcontextprotocol/sdk/server/streamableHttp.js"; import express from "express"; import { z } from "zod"; import { storefrontRequest } from "./storefrontClient.js"; // straight from Lab 3.6 function buildServer() { const server = new McpServer({ name: "shopify-tools", version: "1.0.0" }); server.registerTool( "search_products", { title: "Search Products", description: "Search the store catalog for products matching a text query.", inputSchema: { query: z.string().default("") }, }, async ({ query }) => { const data = await storefrontRequest(` query($query: String) { products(first: 5, query: $query) { edges { node { title priceRange { minVariantPrice { amount currencyCode } } variants(first: 1) { edges { node { id } } } } } } } `, { query }); const products = data.products.edges.map((e) => ({ title: e.node.title, price: e.node.priceRange.minVariantPrice.amount, currency: e.node.priceRange.minVariantPrice.currencyCode, variantId: e.node.variants.edges[0]?.node.id ?? "", })); return { content: [{ type: "text", text: JSON.stringify({ products }) }] }; } ); return server; } const app = express(); app.use(express.json()); // Stateless mode: a fresh server + transport per request. Simple, and enough // for tools with no cross-call session state (Module 5's cart tool needs a // session id of its own if you bring it into this same server). app.post("/mcp", async (req, res) => { const transport = new StreamableHTTPServerTransport({ sessionIdGenerator: undefined }); const server = buildServer(); await server.connect(transport); await transport.handleRequest(req, res, req.body); res.on("close", () => { transport.close(); server.close(); }); }); app.listen(3200, () => console.log("MCP server listening on :3200/mcp"));
Tested end to end, both transports. This server was driven by a real @modelcontextprotocol/sdk client — not a mock — over both a local stdio subprocess and this real HTTP transport: a genuine MCP handshake, listTools() correctly advertising search_products, and callTool() round-tripping arguments and returning the tool's real output shape. Both passed.

Step 2 — Connect Claude Code to your own server

node mcpServer.js # in a separate terminal claude mcp add --transport http my-shop-tools http://localhost:3200/mcp

Ask Claude Code to search your catalog in plain language, exactly like Topic 4.2's demo against Shopify's own Storefront MCP — except this time it's calling a tool you wrote, with whatever logic and guardrails you put in it.

Acceptance checklist

  • claude mcp list shows your server connected, and its tool is discoverable
  • A natural-language product question in Claude Code returns real catalog data through your own tool, not Shopify's Storefront MCP
  • The tool's logic is unchanged from Module 5 — only how it's reached is different
  • The server responds correctly whether reached over stdio or HTTP
4.4 · Briefing + Demo

Universal Commerce Protocol (UCP)

MCP connects an agent to tools. UCP is a level up: a standard for an agent to discover and transact with any participating merchant, not just one you've already integrated with.

🌐

What UCP is for

Universal Commerce Protocol is an open standard from Shopify and Google for agent-driven commerce: capability discovery, negotiation, cart/checkout, and order monitoring, expressed the same way across any merchant that implements it. The goal is that a shopping agent doesn't need a bespoke integration per store — it discovers what a UCP-enabled store supports and transacts against a common interface, the same spirit as MCP but one layer up, aimed at commerce specifically rather than tools in general.

The demo walks through inspecting capability discovery against a UCP-enabled endpoint live.

⚠️ This is one of the newest, fastest-moving standards in the whole program. UCP was only announced in 2025 and its exact discovery endpoints and payload shapes are still settling. Check Shopify's current published UCP documentation before this session rather than treating anything specific here as fixed — the concept (standardized discovery and negotiation across merchants) is the durable part; the exact wire format is not something to memorize yet.
4.5 · Briefing

Agentic Commerce Protocol (ACP) & the Wider Landscape

UCP isn't the only standard chasing "let an AI agent shop on a user's behalf." A walkthrough-only comparison — no live demo, since it's a competing ecosystem, not one built on Shopify's own stack.

🛒

ACP: OpenAI + Stripe

Agentic Commerce Protocol is what currently powers ChatGPT's "Instant Checkout" — a shopper completes a purchase from inside a ChatGPT conversation, with Stripe handling payment. It's narrower and more vertically integrated than UCP: built around one assistant (ChatGPT) and one payments partner (Stripe), focused specifically on completing a checkout rather than the broader discovery-and-negotiation scope UCP targets.

StandardBacked byScope
MCPAnthropic (open standard)Connecting any LLM app to any tool/data source
UCPShopify + GoogleCross-merchant agent discovery, negotiation, cart/checkout, order monitoring
ACPOpenAI + StripeCheckout completion inside ChatGPT specifically

Treat this as an actively contested space rather than a settled one — expect the boundaries between these (and others that emerge) to keep shifting well past this program.

4.6 · Briefing

Shopify Sidekick & Agentic Storefronts

Two more places Shopify's own AI shows up — one merchant-facing, one about being found by AI shopping assistants you don't control at all.

🤝

Sidekick and MCP-based app extensions

Sidekick is Shopify's merchant-facing AI assistant built into the Admin — natural-language actions like "show me my best-selling products this month" or drafting a discount. MCP-based app extensions are how a third-party app (in principle, one you built) can plug its own capabilities directly into Sidekick's action surface, rather than being a separate screen the merchant has to navigate to.

🔭

Agentic Storefronts

This is the flip side of Topics 4.4–4.5: making a merchant's catalog discoverable and transactable from inside ChatGPT, Microsoft Copilot, Google Gemini, and Google's AI Mode — surfaces the merchant doesn't own or control. A store becomes an "agentic storefront" by implementing the discovery/transaction standards (UCP, ACP, or both) those assistants speak, so a shopper never has to leave their AI assistant of choice to buy something.

The thread connecting all six topics this module: Shopify already gives you a lot for free — MCP servers, Sidekick extensions, agentic-storefront discoverability. Everything built by hand in Modules 3–4 is what you reach for when you need control, custom logic, or guardrails those built-in surfaces don't give you.

🔭

Module 8's capstone folds it — alongside the shopping agent from Module 5, the admin-ops agent from Module 6, and the RAG support agent from Module 7 — into one multi-agent, orchestrated platform, with this MCP server as one of several standardized surfaces other agents and clients can reach.
