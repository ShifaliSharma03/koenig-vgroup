2.1 · Briefing + Lab

Anthropic Messages API Deep Dive

Module 1 called the Messages API through simple, one-shot scripts. This session goes under the hood: how requests are structured, how streaming works, and how to keep a multi-turn conversation coherent and affordable.

📨

Anatomy of a request

Every call takes a model, a max_tokens cap, an optional top-level system prompt, and a messages array of {role, content} turns — the same shape you used for the React chat widget's local state in Lab 1.6.

import Anthropic from "@anthropic-ai/sdk"; const client = new Anthropic(); const response = await client.messages.create({ model: "claude-sonnet-5", max_tokens: 1024, system: "You are a concise Shopify merchandising assistant.", messages: [ { role: "user", content: "Suggest a name for a waterproof backpack." } ], }); console.log(response.content[0].text);
🌊

Streaming responses

For anything user-facing — like the chat widget from Module 1 — streaming tokens as they're generated feels dramatically faster than waiting for the full response, even though total generation time is the same.

const stream = client.messages.stream({ model: "claude-sonnet-5", max_tokens: 1024, messages: [{ role: "user", content: "Write a short, upbeat product description for an insulated water bottle." }], }); stream.on("text", (chunk) => process.stdout.write(chunk)); await stream.finalMessage();
🔁

Multi-turn context is sent, not remembered

There's no server-side session — every request resends the full messages history the app wants Claude to consider. As a conversation grows, so does the token count (and cost) of every subsequent call.

💾

Prompt caching for cost/latency

Marking a stable block (a long system prompt, a product catalog excerpt) with cache_control: { type: "ephemeral" } lets Claude reuse it across calls instead of reprocessing it every time — meaningfully cutting cost and time-to-first-token for anything that resends the same large context repeatedly.

Lab: stream a response from a Node.js script

Write a small script that opens a stream against the Messages API and prints tokens to the console as they arrive, then prints the total input/output token usage from the final message once the stream completes.

  • Text appears incrementally in the terminal, not all at once
  • The script reads ANTHROPIC_API_KEY from the environment, never hardcoded
  • Final usage (input_tokens/output_tokens) is printed after the stream ends

2.2 · Briefing + Lab

Tool Use / Function Calling

Tool use is what turns Claude from a text generator into something that can act — look something up, run a calculation, or (starting Module 3) touch a real Shopify store. Everything in the rest of the program builds on this pattern.

🧰

Defining a tool schema

A tool is a name, a description Claude uses to decide when to call it, and a JSON Schema describing its inputs. Claude never executes anything itself — it only returns a request to call a tool; your code runs it and sends the result back.

const tools = [{ name: "get_stock_level", description: "Look up current inventory count for a product SKU.", input_schema: { type: "object", properties: { sku: { type: "string" } }, required: ["sku"], }, }];
🔀

The tool-call round trip

  1. Send — call messages.create with tools attached
  2. Inspect — check response.stop_reason === "tool_use"
  3. Execute — run your actual function with the arguments Claude provided
  4. Reply — send the result back as a tool_result content block in a new user turn, then call the API again
🎯

Choosing vs. forcing a tool call

tool_choice: { type: "auto" } lets Claude decide whether a tool is needed at all (the default for most agents). { type: "tool", name: "..." } forces a specific tool call — useful for narrow, single-purpose extraction tasks where you always want structured output, never prose.

⚠️ Never trust tool arguments blindly. Claude generates the arguments to a tool call from the conversation — validate and sanity-check them in your code exactly as you would any other untrusted input, especially once tools start writing data in later modules.

Lab: a calculator/lookup agent

Build a Node.js agent with a single custom tool — a calculator (add/subtract/multiply/divide) or a static product lookup table, either is fine. Wire the full round trip above end to end.

  • Asking a question the tool can't answer gets a plain-text reply, no tool call
  • Asking something the tool can answer triggers a real tool call with correct arguments
  • The tool's actual result (not a guess) appears in Claude's final answer
  • An invalid input (e.g. divide by zero, unknown SKU) is handled without crashing the script

2.3 · Briefing + Lab

Claude Agent SDK Essentials

The Claude Agent SDK packages the request → tool-call → result loop from 2.2 into a managed agent runtime, and adds the pieces a hand-rolled loop doesn't give you for free: custom MCP tool servers, permission modes, subagents, and hooks.

🔄

The agent loop, managed for you

Instead of manually checking stop_reason and looping, the SDK's query() (or equivalent runner) handles the tool-call round trip internally — you register tools and get back a stream of agent turns, including intermediate tool calls and results.

🖥️

Custom tools via createSdkMcpServer

Rather than defining raw tool schemas by hand as in 2.2, the SDK lets you expose a set of typed Node.js functions as an in-process MCP server the agent can call directly — the same shape of tool you'll later expose over the network in Module 7's custom MCP server lab.

import { createSdkMcpServer, tool } from "@anthropic-ai/claude-agent-sdk"; import { z } from "zod"; const stockServer = createSdkMcpServer({ name: "inventory-tools", tools: [ tool("get_stock_level", "Look up inventory for a SKU", { sku: z.string() }, async ({ sku }) => ({ content: [{ type: "text", text: `SKU ${sku}: 42 in stock` }] }) ), ], });
🔐

Permission modes

The SDK supports permission modes ranging from prompting before every tool call to fully autonomous execution. For anything that can write data — draft orders, webhooks — default to a mode that requires explicit approval; we'll tighten this further with confirmation gates in Module 5.

🧩

Subagents and hooks, previewed

Subagents let one agent delegate a sub-task to another agent with its own tools and system prompt — the basis for Module 8's multi-agent orchestration. Hooks run your code at defined points in the loop (before/after a tool call) — useful for logging, guardrails, or blocking a disallowed action outright.

Lab: scaffold an agent project

Set up a new Node.js/TypeScript project using the Claude Agent SDK. Register the inventory-tools-style MCP server above (or your own equivalent), and confirm the agent calls it correctly from a natural-language prompt.

  • Project runs with tsc / ts-node without type errors
  • At least one custom tool is registered via createSdkMcpServer
  • A natural-language prompt that should trigger the tool actually does
  • Permission mode is set deliberately, not left on a default you haven't checked

2.4 · Briefing

Structured Outputs & Reliability

An agent tool call that returns malformed data doesn't just look bad — downstream code that expects a specific shape can crash or silently corrupt state. This is about making failures loud and recoverable instead of silent.

📐

JSON-schema-constrained responses

Building on the output-constraint prompting from Module 1's Lab 1.3, tool input_schemas (2.2) already give you schema-validated inputs to your tools. For a tool's output back to Claude, keep the same discipline: a fixed, documented shape the rest of your code can parse without guessing.

✅

Validate before you trust

Parse and validate every tool result — both what Claude sends into your tool and what your tool sends back — with a schema library like zod rather than assuming the shape is correct.

const StockResult = z.object({ sku: z.string(), inStock: z.number().int() }); const parsed = StockResult.safeParse(rawToolResult); if (!parsed.success) { // return a structured error to Claude, not a crash }
🔁

Retries and backoff

Transient failures (rate limits, network blips) should retry with backoff automatically. A tool call that fails for a logical reason (SKU doesn't exist) should not retry — it should return a clear error result so Claude can respond appropriately, e.g. telling the shopper the item wasn't found.

Fail loud, not silent: a tool that swallows an error and returns an empty/default result is worse than one that throws — it lets a wrong answer look confident. Surface failures as explicit, typed error results.
2.5 · Briefing

Conversation Memory & Guardrails

As agents run longer conversations with more tool calls, two problems compound: the context window fills up, and the surface area for something to go wrong (or be abused) grows. This session is about managing both deliberately.

🧠

Context window management

Revisiting Module 1's point that context is resent every call: a long-running agent needs a strategy once history approaches the model's limit — truncating oldest turns, or summarizing older parts of the conversation into a shorter recap the agent can still act on.

✂️

Summarization strategies

A common pattern: once history crosses a token threshold, use a cheap, fast call (Haiku 4.5) to compress older turns into a short summary, keep the most recent turns verbatim, and continue the conversation on the combined, shorter context.

🛡️

Input/output guardrails

Input guardrails screen what reaches the model (rate limiting, rejecting obviously malicious input). Output guardrails check what the model wants to do before it happens — especially before any tool call that costs money or changes state.

⚠️ Safe defaults for state-changing actions. Any tool that writes data (creates an order, sends a message, changes inventory) should default to requiring explicit confirmation until proven safe in testing — this is the same principle behind the permission modes in 2.3, and the confirmation gates you'll build explicitly in Module 5.
2.6 · Lab

Standalone Multi-Tool Agent (Node.js)

The capstone lab for this module: combine everything from 2.1–2.5 into one reusable agent skeleton — no Shopify yet, that starts in Module 3, where these exact tools get swapped for real Storefront/Admin API calls.

Requirements

  • 3+ custom tools (e.g. product lookup, order-status lookup, a calculator) registered via the Agent SDK
  • Conversation memory that persists correctly across multiple turns in one run
  • Structured, schema-validated JSON output from every tool, per 2.4
  • At least one guardrail — a confirmation step or a rejected out-of-scope request

Try prompting Claude Code with something like:

"Scaffold a Node.js/TypeScript Claude Agent SDK project called multi-tool-agent. Register three tools via createSdkMcpServer: 1. get_product_info(name: string) — returns a mock product record 2. get_order_status(orderId: string) — returns a mock order status 3. calculate_discount(price: number, percent: number) — returns the discounted price Validate every tool's output with zod before returning it to the agent. Keep full conversation history across turns in a REPL loop so I can ask follow-up questions that reference earlier answers."

Acceptance checklist

  • All three tools are called correctly from natural-language prompts
  • A follow-up question referencing an earlier turn (e.g. "what about that same order?") resolves correctly
  • An invalid tool result is caught by validation, not passed through silently
  • You can explain exactly what happens at each step of the request → tool-call → result loop
Keep this project. This is the literal skeleton Module 3 wires up to real Shopify Storefront and Admin API calls — the mock tools get replaced, but the agent structure, validation, and memory handling stay the same.
