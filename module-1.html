1.2 · Briefing

How LLMs Actually Work

Everything an AI agent does later in this program — why it "forgets" things, why it costs money per request, why one model feels smarter than another — traces back to four ideas. Get these right now and a lot of later debugging gets easier.

🔤

Tokens are not words

Claude reads and writes in tokens — chunks of text that are often smaller than a whole word. Common short words are usually one token; longer or unusual words get split into pieces.

// Roughly how a sentence gets tokenized (illustrative, not exact) "Shopify agents are useful" → ["Shop", "ify", " agents", " are", " useful"] // 5 tokens, 4 words

This matters practically: Claude's API is billed per token (input + output), and every limit you'll hear about — context window, max output — is measured in tokens, not words or characters.

🧠

The context window is working memory, not storage

The context window is the maximum amount of conversation (in tokens) Claude can "see" at once — your messages, its replies, any documents or tool results you've included. As of this program, Claude Sonnet 5 (our default model) and Opus 4.8 support up to 1,000,000 tokens of context; Haiku 4.5 supports 200,000 tokens. That's roughly 750,000 words at the high end — most of a very long novel.

Nothing persists after a conversation ends. If an application wants Claude to "remember" earlier turns, it has to resend that history as part of the context window on every request — there's no hidden long-term memory. We'll cover strategies for managing this deliberately (summarization, trimming) once we build multi-turn agents in Module 2.

🌡️

Temperature controls randomness, not "creativity"

Temperature is a setting (typically 0–1) that controls how much the model varies its word choices. At temperature 0, the same prompt reliably produces close to the same output every time — good for anything that needs to be predictable (structured data extraction, classification). Higher temperatures introduce more variety — useful for brainstorming or creative copy, risky for anything downstream code needs to parse.

🔎

A quick word on embeddings

You'll hear "embeddings" again when we cover Retrieval-Augmented Generation (RAG) later in the program. In short: an embedding turns a piece of text into a list of numbers (a vector) that captures its meaning, so a computer can compare how similar two pieces of text are — the basis for search that understands intent, not just keyword matching.

1.3 · Briefing + Lab

Prompt Engineering That Holds Up in Production

A prompt that works once in a chat window is not the same as a prompt that works reliably inside an application. This is the shift from "chatting" to engineering.

💬

System prompt vs. user prompt

The system prompt sets durable behavior — role, tone, constraints — that should hold across an entire conversation. The user prompt carries the specific, per-turn request.

// System prompt (set once) "You are a product copywriter for an outdoor gear store. Always respond with a single JSON object matching: { title: string, description: string, seo_keywords: string[] } Never include text outside the JSON object." // User prompt (per request) "Product: Trailblazer 40L Hiking Backpack, waterproof, 12 external pockets"
🔁

Few-shot examples beat more instructions

When output is inconsistent, adding 1–2 concrete examples usually fixes it faster than adding more rules in prose.

Before (inconsistent): "Write a short product description." → sometimes a sentence, sometimes a bullet list, sometimes includes a price it invented.

After (few-shot): include 2 example input/output pairs in the prompt showing the exact desired shape. Output consistency jumps immediately.

🧩

Chain-of-thought, used deliberately

For multi-step reasoning (e.g. "does this product need a size variant, and if so which sizes"), letting the model reason step-by-step before answering improves accuracy — but in a production response, that reasoning is usually hidden from the end user and only the final answer is returned.

🔒

Output constraints prevent downstream bugs

Anything parsing the model's output — a database column, a UI component, another function — needs a predictable shape. State the format explicitly and validate it.

Respond with only valid JSON, no markdown fences, matching exactly: { "title": string, "description": string, "seo_keywords": string[] }

Lab: build a prompt that survives edge cases

Starting from a loose prompt ("write a product description"), iterate it in the Claude Console until it reliably returns the JSON shape above. Test it against all four of these before calling it done:

  • A normal, well-formed product name
  • An empty or missing product title
  • A non-English product name
  • A product name containing HTML or special characters

Done means: valid, parseable JSON on all four — not just the first one.

1.4 · Briefing + Demo

Vibe Coding Fundamentals

"Vibe coding" gets used loosely — here it means a specific, disciplined loop with Claude Code, not handing over the keyboard and looking away.

The loop

  1. Plan — write the goal, constraints, and edge cases in a sentence or two before opening Claude Code
  2. Prompt — describe the task clearly, including what "done" looks like
  3. Review the diff — read every changed file before accepting; ask Claude Code to explain any line you don't understand
  4. Iterate — request specific changes rather than re-describing the whole task from scratch

Tool permissions

Claude Code asks before taking actions like editing files or running shell commands. Treat these prompts as real decision points, not a formality to click through — if a requested action doesn't make sense for the task, say no and ask what it's for.

What a good review actually checks

  • Does the diff match what you actually asked for?
  • Are there side effects you didn't expect (extra files, changed configs)?
  • Is error handling reasonable, or does it silently swallow failures?
  • Would you be comfortable explaining this code to someone else?
Addressing the obvious pushback: "isn't this just letting the AI write bad code?" — only if you skip the review step. The discipline of reading every diff before accepting is vibe coding; skipping it is something else entirely.
1.5 · Lab

Vibe-Code a Product Data Utility (Node.js)

Your first full pass through the loop above, on a small, real task.

Starting point

You'll be given a sample product CSV, intentionally a little messy:

name,description,price Trailblazer 40L Backpack ,Waterproof hiking pack,129.99 CAMP STOVE MINI,,45.00 Insulated Water Bottle 1L,Keeps drinks cold 24h,22.50

Notice the stray whitespace, inconsistent casing, and one missing description — all deliberate.

The task

Open Claude Code and describe the goal: build a Node.js script that reads the CSV, cleans up the fields (trim whitespace, normalize casing), and generates a one-line SEO-friendly description for any product missing one — using the Claude API and the prompt discipline from 1.3.

Try prompting Claude Code with something like:

"Build a Node.js script (Node 20+, ESM) that: 1. Reads products.csv (name, description, price) 2. Trims whitespace and normalizes name casing to Title Case 3. For any row with an empty description, calls the Claude API to generate one SEO-friendly sentence 4. Prints the cleaned, complete product list to the console Use the @anthropic-ai/sdk package and read the API key from process.env.ANTHROPIC_API_KEY."

Acceptance checklist

  • Script runs with node against the sample CSV without errors
  • Whitespace and casing issues are visibly fixed in the output
  • The row with a missing description now has a generated one
  • You read and understood every part of the diff before accepting it
Stuck? Common issues: ANTHROPIC_API_KEY not set in your shell/.env, Node running an older cached version (check with node --version), or the CSV parser choking on the trailing comma-less last line — ask Claude Code to add error handling for malformed rows rather than debugging it manually.
1.6 · Lab

Vibe-Code a React Chat UI Skeleton

A UI-only exercise — no backend calls yet. This component gets wired to a real agent later in the program, so the shape you choose now matters.

What to build

A functional React component with: a scrollable message list, a controlled text input, and a "send" handler that appends to the list (no network call yet — just local state).

Use this state shape

Keep messages as an array of role/content pairs — this exact shape gets reused when the widget is wired to a live agent later:

const [messages, setMessages] = useState([ { role: "assistant", content: "Hi! Ask me about our products." }, ]); // role is "user" | "assistant"

Try prompting Claude Code with something like:

"Build a React functional component called ChatWidget. State: messages (array of {role, content}), and inputValue (string). Render the message list scrollable, with user/assistant messages visually distinguished. A controlled input + send button appends a new {role: 'user', content: inputValue} message and clears the input. No API calls — just local state for now. Use plain CSS, no UI library."

Acceptance checklist

  • Typing and submitting a message appends it to the visible list
  • The input clears after send
  • The component renders sensibly with zero messages (empty state)
  • Message state uses the {role, content} shape above
Save this. Commit the component to your own local git repo — you'll extend it directly rather than rebuild it when the shopping agent gets a real UI later in the program.
