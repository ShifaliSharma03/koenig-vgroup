3.1 · Briefing + Demo

Shopify Architecture for Developers

Before touching any API, it helps to know what you're actually pointed at — the difference between an account, a store, and an app trips up a lot of first-time Shopify developers.

🏗️

Partner accounts and dev stores

A Partner account is your developer identity with Shopify — free to create, and it's where you spin up development stores: full, free, disposable Shopify stores meant for building and testing, never for real sales. Every lab in this program runs against a dev store you create yourself.

🔌

Custom apps vs. public apps

A custom app is built for and installed into exactly one store — the right choice while you're learning and building for a single dev store, which is what this program uses throughout. A public app is built to be installed into any merchant's store, distributed via the Shopify App Store, and requires the OAuth flow covered in Topic 3.2.

One thing to know before Topic 3.2: as of January 1, 2026, Shopify retired the old "create a custom app from inside the store's Admin" flow for new apps. Custom apps are now created and managed from the Dev Dashboard (dev.shopify.com/dashboard) — a separate site from the store Admin, shared across your Partner organization. The underlying idea (one app, one store, scoped access) hasn't changed, only where you go to set it up.

🧭

Three surfaces, three purposes

SurfaceAudienceAccessed via
AdminThe merchantAdmin dashboard (browser) + Admin API (GraphQL)
StorefrontThe shopperThe online store + Storefront API (GraphQL)
CheckoutThe shopper, at time of paymentShopify-hosted checkout, extensible but not fully custom

Nearly everything this module and Module 4 build touches the first two — Admin API for anything an agent needs to read or write on the merchant's behalf, Storefront API for anything a shopper-facing agent needs.

Demo: tour of a live dev store and the Dev Dashboard

A guided walkthrough — follow along in your own store and Partner organization:

  • Store Admin → Apps — where you'll see your app listed once it's installed from the Dev Dashboard, and where any legacy custom apps created before January 2026 still live
  • dev.shopify.com/dashboard — the separate site where new apps are created, installed, and their credentials retrieved; their access scopes are actually declared in a local shopify.app.toml file and pushed via the CLI (used directly in Topic 3.2)
  • Store Admin → Products — where the catalog data your agent will query actually lives
  • Store Admin → Orders — where draft orders created via the Admin API show up
  • Store Admin → Settings → Notifications — where webhook-triggering events like order confirmation emails originate
3.2 · Briefing + Lab

Authentication, OAuth & Access Scopes

Every API call this module makes needs a token, and every token needs scopes. Getting this right early avoids a class of bugs that otherwise looks like "the API is broken" but is actually "the token can't do that."

🔑

Custom app tokens via the Dev Dashboard — the path this program uses

Since January 2026, a custom app's credentials no longer show up as a single static token sitting in the store Admin. You still start from Store Admin → Settings → Apps → Develop apps, but that screen now just hands off to Build apps in Dev Dashboard — a separate site (dev.shopify.com/dashboard) where an app is just a name and an identity. There's no checkbox screen for Admin API scopes there at all — scopes are declared in a shopify.app.toml file inside your own local project, edited by hand and pushed with the Shopify CLI (covered step by step in the lab below). Once installed, the app's Dev Dashboard Settings tab issues a Client ID and Client secret instead of a token — your code exchanges those for an access token itself using the client credentials grant, a direct, no-redirect exchange that's a good fit for a single app talking to a single store you control.

// Exchange client ID + secret for an Admin API access token async function getAdminAccessToken() { const res = await fetch( `https://${process.env.SHOPIFY_STORE_DOMAIN}/admin/oauth/access_token`, { method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.stringify({ client_id: process.env.SHOPIFY_APP_CLIENT_ID, client_secret: process.env.SHOPIFY_APP_CLIENT_SECRET, grant_type: "client_credentials", }), } ); const data = await res.json(); return data.access_token; // use as X-Shopify-Access-Token } // Response shape: { access_token, scope, expires_in: 86399 }

That expires_in matters: unlike the old static custom-app token, this one expires in 24 hours. Any script that runs longer than that needs to request a fresh one before the old one lapses — covered in the lab below.

🔁

OAuth for public apps

A public app can't pre-generate a token because it doesn't know which store will install it. Instead: the merchant is redirected to Shopify to approve the app's requested scopes, Shopify redirects back with an authorization code, and the app exchanges that code for an access token server-side. You won't build this in the program, but recognizing the flow matters if you ever ship a distributable app.

🛡️

Read vs. write scopes

Scopes are granular and explicit — a token can only do what it was explicitly granted, nothing more.

ScopeGrants
read_productsQuery product/collection data
read_ordersQuery existing orders
read_draft_ordersQuery existing draft orders
write_draft_ordersCreate/update draft orders — the agent's main "write" path
write_ordersCreate/modify real orders directly (used sparingly)
read_customersQuery customer records
read_inventoryQuery stock levels

Editing the scopes line in shopify.app.toml and running shopify app deploy doesn't retroactively apply to an already-installed app — the new scope set only takes effect once you reinstall the app on the store and approve the updated permission list.

🔒

The Protected Customer Data gate — lives at partners.shopify.com, not the Dev Dashboard

Granting read_orders or read_customers in shopify.app.toml is not enough on its own. Any Admin API object touching customer PII (orders, customers) sits behind a second, distinct approval called Protected customer data access — required even for an app you own, installed only on your own dev store. It's easy to miss because it doesn't live anywhere in the Dev Dashboard (dev.shopify.com/dashboard) — despite that being where you create the app, declare scopes, and install it. It's on the separate, older Partners site instead: partners.shopify.com → your app → API access requests → Protected customer data access → Request access.

Skip it and a query that looks perfectly correct fails with an approval-style error — the token and declared scopes are fine; this is a separate gate entirely. For a dev-store-only app like this one, it needs no review, just checking the box and saving.

Lab: create a custom app in the Dev Dashboard and generate a scoped Admin API token

  1. Create the app — from Store Admin → Settings → Apps → Develop apps, click Build apps in Dev Dashboard, then create a new app (e.g. "Agentic AI Bootcamp") and confirm. This just names the app — it doesn't ask for scopes or a target store yet
  2. Install the Shopify CLI and link a local project — run npm install -g @shopify/cli@latest, then in a new project folder run shopify app config link. It walks you through a browser device-login, picking your Partner organization, and choosing "connect it to an existing app" → your app from step 1. This generates a shopify.app.toml file, pre-filled with your app's Client ID and a blank scopes field
  3. Declare scopes in shopify.app.toml — this file, not any web screen, is where Admin API scopes actually live. Edit its [access_scopes] block: scopes = "read_products,read_orders,write_draft_orders,read_customers" — resist listing everything "just in case"
  4. Deploy the new version — run shopify app deploy and confirm "Yes, release this new version." Every edit to shopify.app.toml needs a fresh deploy to actually take effect on Shopify's side
  5. Install the app on your dev store — back in the Dev Dashboard, open the app's Overview tab, click Install app, and select your dev store (must be in the same Partner organization). Review and approve the consent screen it redirects you to
  6. Request Protected customer data access — go to partners.shopify.com (not the Dev Dashboard), open your app, API access requests → Protected customer data access → Request access, check the box, choose applicable reasons, and Save
  7. Copy your credentials — in the app's Dev Dashboard Settings tab, copy the Client ID and Client secret into your .env file (there's no single access token shown here anymore — that's requested in the next step)
  8. Exchange them for a token programmatically — write a small Node.js helper that POSTs to /admin/oauth/access_token as shown above, caches the returned token, and requests a new one once it's close to its 24-hour expiry

Acceptance checklist

  • App created in the Dev Dashboard and linked to a local project via shopify app config link, within your own Partner organization
  • Only the scopes actually needed for this module are declared in shopify.app.toml and deployed before installing
  • Protected customer data access requested and approved at partners.shopify.com, so read_orders/read_customers queries don't fail with an approval error
  • Client ID and secret are stored in .env, never committed to git
  • Your token-exchange helper successfully authenticates a test GraphQL request (e.g. a simple shop { name } query), and re-requests a token once the cached one is near expiry
⚠️ Dev store only. This token can create draft orders and read customer data — never point it at a production store, even out of curiosity.

3.3 · Briefing + Lab

Storefront API (GraphQL) — Products & Cart

The Storefront API is what a shopper-facing agent uses to browse the catalog and build a cart — everything Module 4's shopping agent needs before checkout.

🛰️

Getting a Storefront API token: the Headless channel

Storefront API access doesn't come from the same place as the Admin API token in Topic 3.2 — it comes from installing the free Headless sales channel (from the Shopify App Store) on your dev store, then clicking Create storefront. That generates a public token (safe for client-side use) and a private token (server-side only — this is the one a Node.js backend uses, sent as the Shopify-Storefront-Private-Token header). Under the storefront's Storefront API permissions, enable at minimum unauthenticated_read_product_listings, unauthenticated_read_product_inventory, unauthenticated_read_checkouts, and unauthenticated_write_checkouts — the four scopes that cover product browsing and the Cart API below.

⚠️ Dead end to avoid: the Dev Dashboard's Settings tab also shows a "Storefront API" card with a "Manage" button. Clicking it does not reveal a token — it routes to the Partners dashboard's "API access requests" page, a completely different feature for requesting extra protected scopes ahead of App Store review. The real Storefront token only ever comes from the Headless channel above.
📦

Querying products, collections and search

// Storefront API — product search by title/keyword query searchProducts($query: String) { products(first: 3, query: $query) { edges { node { title priceRange { minVariantPrice { amount currencyCode } } variants(first: 1) { edges { node { id title availableForSale } } } } } } } // Header: Shopify-Storefront-Private-Token: {your private token} // node.variants.edges[0].node.id is the merchandiseId a cart mutation needs
Pitfall worth knowing up front: when a tool's search query is empty (a shopper asking "what do you sell?" rather than naming a product), pass an empty string "" for $query, not null. Confirmed against a live dev store: "" returns the unfiltered catalog, while an explicit null returns zero products — the opposite of what you might expect, and easy to get backwards.
In GraphiQL's Variables panel: the variable name goes in without the $ — the $ only belongs inside the query document itself. Use { "query": "backpack" } or { "query": "" }; typing $query there directly is invalid JSON and throws a parse error.
🛒

The current Cart API

Shopify deprecated the old Checkout API in favor of the Cart API — cartCreate, then cartLinesAdd to add items, then read checkoutUrl off the cart to hand the shopper a working payment link.

// Create a cart, then read its checkout URL mutation { cartCreate { cart { id checkoutUrl } } } // Add a line item to that cart mutation { cartLinesAdd(cartId: "gid://shopify/Cart/...", lines: [ { merchandiseId: "gid://shopify/ProductVariant/...", quantity: 1 } ]) { cart { checkoutUrl } } }

On any Shopify plan below Plus, a custom page can't collect card payments directly (PCI compliance) — checkoutUrl is the actual, complete payment path for a self-checkout shopping agent: the shopper pays on Shopify's own hosted checkout page, not inside the conversation. This is a genuinely different object and use case from the Admin API's draft orders in Topic 3.4, which a merchant or agent builds on the customer's behalf — Module 4's shopping agent uses the Cart API almost exclusively for this reason.

⚠️ Dev stores are always password-protected — Shopify doesn't allow disabling it on a development store at all (only on a paid or transferred store). Visiting a fresh checkoutUrl in a browser that's never unlocked that store hits the password gate first, and on a dev store that redirect can drop the original checkout destination and land you back on the plain homepage instead. Fix: open your store's root URL (https://your-store.myshopify.com/) in that browser first, enter the storefront password once, then open the checkoutUrl — an already-unlocked browser goes straight to checkout.

Lab: run queries in Shopify's GraphiQL app

Install the Headless channel on your dev store and create a storefront to get your private access token (see above), then open Shopify's GraphiQL app at shopify-graphiql-app.shopifycloud.com/login to run and inspect queries interactively before wiring them into code — it isn't listed in the Shopify App Store, so go straight to that URL rather than searching for it.

  • Headless channel installed and a storefront created, with its private access token saved to .env
  • Successfully queried at least 3 products by title/price using the Storefront API
  • Created a cart via cartCreate and captured its checkoutUrl
  • Added a line item via cartLinesAdd and confirmed it reflects in the cart
  • Can explain why checkoutUrl replaces the deprecated Checkout API

3.4 · Briefing + Lab

Admin API (GraphQL) — Orders, Draft Orders & Customers

This is the merchant-facing counterpart to 3.3 — where an agent reads order/customer history on the store owner's behalf, and can build a draft order and invoice link for a sale it's handling directly, rather than a shopper checking out live.

🧾

orderCreate vs. draftOrderCreate

These are both Admin API writes, and neither is what a self-checkout shopping agent uses for a normal purchase — that's Topic 3.3's Cart API and checkoutUrl. draftOrderCreate is for a merchant- or agent-initiated sale built on the customer's behalf — think a phone order or an admin-side agent assembling an order from a conversation — and returns an invoiceUrl the customer pays separately. orderCreate records an order that was already paid through some other channel entirely. Both matter for Module 5's admin-scoped agent; this lab just gets the mechanics working.

🔗

Draft order → invoice link

// Create a draft order and get its invoice URL mutation { draftOrderCreate(input: { lineItems: [{ variantId: "gid://shopify/ProductVariant/...", quantity: 1 }] }) { draftOrder { id invoiceUrl } } }
🔍

Customer and inventory queries

Reading customer records (order history, contact info) and inventoryItem/inventoryLevel data lets an agent answer "have I ordered this before?" or "is this in stock?" — both reused directly in Module 4's shopping agent and Module 6's personalization labs.

Lab: create a draft order and fetch its invoice URL

Using your Topic 3.2 token, run draftOrderCreate against a real product variant in your dev store and confirm the returned invoiceUrl actually opens a payable invoice.

  • draftOrderCreate ran successfully against your dev store
  • The response includes a usable invoiceUrl
  • At least one customer or inventory query returns real dev-store data
  • Can explain when to use draftOrderCreate vs. orderCreate
3.5 · Briefing

Scoping an AI Agent Safely

With both APIs now in reach, it's worth pausing on a design decision that shapes every lab from here forward: not every part of an agent needs the same level of access.

🎯

Minimum-necessary scopes, mapped to capability

Before writing a tool, ask what it actually needs to do — a product-search tool needs read_products and nothing else. Granting it write_orders "in case it's useful later" is exactly the kind of over-scoping that turns a minor bug into a real incident.

🪪

Two tokens, not one

A practical pattern used throughout the rest of the program — and one that now maps naturally onto two genuinely different credential sources: a read-only "shopper" token — the Headless channel's Storefront API token from Topic 3.3, which only ever sees read-shaped operations like product search and cart building — and a separate write-capable "admin-actions" token, the Dev Dashboard's Admin API access token from Topic 3.2, scoped to write_draft_orders (and later write_orders in Module 5) and reserved for actions that actually change store state. If the shopper-facing side of the agent is ever compromised or misused, it physically cannot place an order — it's holding the wrong credential entirely.

This isn't paranoia — it's the same instinct behind Module 2's guardrails. Scoping is a guardrail that exists before the agent even runs, rather than one checked at each tool call.

What to build

3.7 · Briefing + Demo

Shopify Native AI — Magic & Sidekick

Shopify ships its own AI tools out of the box. Knowing exactly where they stop is what justifies building a custom agent at all, rather than just pointing merchants at what's already there.

✨

Shopify Magic

Free, built into the Admin: generates product descriptions, marketing copy, FAQ answers, and edited product images from a short prompt. It's fast and requires zero setup — but it's confined to specific Admin fields, isn't scriptable, and can't be embedded into your own product or automated as part of a larger workflow.

🤝

Sidekick

Shopify's chat-based merchant assistant, built into the Admin. It can answer questions about the store and take some actions via MCP-based app extensions (previewed properly in Module 7). Like Magic, it's merchant-facing only — it doesn't talk to shoppers, and you can't redirect its behavior or give it your own tools.

⚖️

Where a custom agent earns its place

Magic and Sidekick solve merchant-side content and admin tasks well. A custom Claude-powered agent is what you need the moment you want shopper-facing conversation, your own tools and business logic, or behavior embedded in your own product rather than inside Shopify's Admin UI — exactly what Module 4 builds.

Demo: Magic vs. a Claude-authored equivalent, side by side

Generate a product description with Shopify Magic for the same product used in your Module 2 labs, then generate an equivalent with the Claude API using your own prompt. Compare:

  • Tone and brand-voice control — how much can you actually steer each one?
  • Whether either invents details not present in the product data
  • How each result could (or couldn't) be produced programmatically, at scale, outside the Admin UI
3.8 · Briefing + Lab

Webhooks & Event-Driven Foundations

Everything so far has been the agent initiating a request. Webhooks flip that: Shopify tells your code when something happens in the store — the foundation Module 5's event-driven agents build directly on.

📡

Registering webhooks

Common topics you'll use this program: orders/create (a new order was placed), inventory_levels/update (stock changed), and app/uninstalled (your app lost access — always handle this one). Each is registered against a URL your code controls, via the Admin API.

🔐

Verifying HMAC signatures

Every webhook request carries an X-Shopify-Hmac-Sha256 header. Recompute the HMAC yourself using your webhook secret and the raw request body, and compare — a mismatch means the request didn't actually come from Shopify.

// Verifying a webhook's HMAC (Node.js, using the raw request body) import crypto from "crypto"; const digest = crypto .createHmac("sha256", process.env.SHOPIFY_WEBHOOK_SECRET) .update(rawBody, "utf8") .digest("base64"); const isValid = crypto.timingSafeEqual( Buffer.from(digest), Buffer.from(hmacHeader) );
⚠️ Never skip HMAC verification. Your webhook endpoint is a public URL — without verification, anyone who finds it can send fake "order placed" events straight into your agent.

Lab: build a lightweight Node.js webhook receiver

Stand up a small Express endpoint that registers for orders/create, verifies every incoming request's HMAC before doing anything else, and logs the order details on success.

  • Registered at least one webhook (e.g. orders/create) against your dev store
  • The receiver correctly verifies the HMAC signature and rejects mismatches
  • Triggering the event in your dev store (e.g. placing a test order) hits your receiver
  • The receiver responds quickly with a 200, deferring any heavy work rather than blocking the response
