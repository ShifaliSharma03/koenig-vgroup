5.1 · Briefing

Agent Architecture for Commerce

Lab 3.6 built one agent talking to one developer over a terminal. A real shopping agent talks to many shoppers at once, each with their own conversation and their own cart — a genuinely different architecture, not just more traffic on the same code.

🧭

Tool selection is the router

There's no hand-written intent classifier deciding "this is a browse request, that's a checkout request." Claude's own tool-use already does that job: give it the right tools and a clear system prompt, and which tool (if any) gets called on a given message is the routing decision. The architecture work is choosing what tools exist and what each one is allowed to do — not writing if/else branches over user text.

👥

One Claude session per shopper, not one for everyone

Lab 3.6's agent.js opened exactly one query() session for the one person typing into its terminal. A chat widget on a live storefront has many shoppers at once, each expecting the agent to remember only their conversation and only their cart. That means one query() session — and, as Topic 5.3 covers, one cart — per browser session, not a single shared session for the whole site.

Lab 3.6 also fed its session from a shared readline interface, which is exactly what caused the confirmation race bug you may have hit there. A web backend has no terminal and no shared readline at all — Topic 5.2 replaces it with a queue built for exactly this: one request in, one reply out, per shopper, with no possibility of that particular race.

💳

Where the agent's job ends

The agent never collects a card number, an address, or any payment detail — it hands the shopper a real checkoutUrl and Shopify's own hosted checkout takes over completely from there. That's not a shortcut; it's the only supported way to accept payment, and it's what keeps PCI compliance entirely off your plate. Because of this, the agent can't know synchronously whether a shopper actually paid — Topic 5.4 covers confirming that after the fact instead of assuming it.

⚠️ Never build a payment form into the conversation. There's no supported way to collect real card details inside a chat UI, and trying to would take on PCI-DSS obligations no lab in this program is set up to meet. The checkoutUrl handoff is the entire integration surface for payment — nothing else touches it.
5.2 · Lab

Product Discovery & Q&A

The first build of the module: a real Express backend that talks to Claude and to your dev store, with one Claude session per shopper instead of Lab 3.6's single terminal session.

🔁

From a readline loop to a request queue

Lab 3.6 fed query() from an async generator that pulled from readline. Here, each shopper's browser session gets its own generator instead, fed by a small queue: an incoming HTTP request pushes a message onto the queue and waits for the matching reply; the generator pulls from the queue and yields it into query(). No shared input source, no race.

Try prompting Claude Code with something like:

"Adapt Lab 3.6's terminal agent into a Node.js/Express backend that can serve many shoppers at once, each with their own conversation. Write chatSession.js exporting a ChatSession class. Internally, use a small message queue - not a single mutable 'next message' slot - where push() either hands a value straight to a reader that's already waiting, or holds it until one asks: this is what keeps two messages from ever racing each other. Feed query()'s async generator from that queue instead of readline. Give the class a send(text) method that pushes a message and returns a promise resolving with the assistant's full reply once the SDK's 'result' message for that turn arrives; chain each send() onto the session's previous one so two messages from the same shopper can never overlap. Then write server.js: an Express POST /api/chat endpoint that takes { sessionId, message }. Keep a Map from sessionId to ChatSession, lazily creating one per new sessionId, each wired to its own query() call that registers Lab 3.6's search_products tool with the same allowedTools requirement - query()'s default permission mode will otherwise stall the first tool call exactly like it did there. Clean up any session that's gone idle for more than 30 minutes so memory doesn't grow without bound. Test it by opening two different sessionIds and confirming neither ever sees the other's conversation history; asking a generic question like 'what do you sell?' and confirming it still returns real catalog results; and firing two messages at the very same session back-to-back without waiting for the first reply, confirming each one comes back matched to its own message rather than swapped."
Tested, not just prompted for. This exact queue-based design was run against a mock query()-shaped stream under three conditions: sequential messages in one session, several messages fired at the same session without waiting for replies, and twenty sessions hammered concurrently. Every reply came back matched to its own message, every time — the queue (not a single mutable "next message" slot) is what makes that hold regardless of timing.
⚠️ allowedTools still matters here. Exactly like Lab 3.6, query()'s default permission mode will otherwise stall the first time search_products should run, with no handler to approve it. Nothing about moving to HTTP changes that requirement — make sure the prompt above (or Claude Code's output) actually includes it.

Acceptance checklist

  • Two different sessionId values get two independent conversations — one never sees the other's history
  • A generic question ("what do you sell?") still returns real catalog results, not an empty list
  • Sending a second message before the first reply arrives never crosses replies between two different sessions
  • Idle sessions are cleaned up rather than accumulating forever in memory
5.3 · Lab

Cart Management & Checkout Link

Add a second tool, backed by Lab 3.6's other Storefront mutations — but this time the cart has to survive across turns, and grow and shrink correctly as the shopper changes their mind.

🔒

Why the model never sees a cart ID

Shopify's cart and line IDs are long opaque GIDs — exactly the kind of token a model can mistype, truncate, or half-remember three turns later. Instead of passing them back and forth as tool arguments, this lab keeps them in a small object closed over by that one shopper's tools — the same "one thing per session" principle from Topic 5.1, just applied to cart state instead of conversation memory. The model only ever passes a variantId and a quantity; it never has to track anything Shopify-specific.

Try prompting Claude Code with something like:

"Add a second tool for managing the shopper's cart, using Lab 3.6's other Storefront mutations - but keep every Shopify cart and line ID out of the model's hands entirely, since those are exactly the kind of opaque token a model can mistype or half-remember a few turns later. Write cartState.js exporting a createCartManager(storefrontRequest) factory. It should track a cartId and a variantId-to-lineId map as private state, and expose one method, addOrSetQuantity(variantId, quantity): the first call for any session should create the cart (cartCreate) and add the line (cartLinesAdd); a later call for a variant already in the cart should update its quantity in place (cartLinesUpdate) rather than adding a duplicate line; and a call with quantity 0 should remove the line (cartLinesRemove) if it's tracked, or do nothing if it was never added. Register a tool called update_cart, taking a variantId and a quantity, that calls this cart manager and returns the resulting checkoutUrl. Construct one cart manager per shopper session, right alongside their query() call from Topic 5.2, so the tool always resolves to that shopper's own cart and no one else's. Test the cart logic against a mocked Storefront client before wiring it to a real store: confirm adding two different variants only calls cartCreate once; confirm calling the tool twice on the same variant updates the line instead of duplicating it; confirm quantity 0 removes a tracked line and is a safe no-op for one that was never added; and confirm removing one line never disturbs any other line in the same cart."
Verified with a mocked Storefront client, exactly as prompted above: adding two different variants calls cartCreate exactly once, not once per item; calling update_cart twice on the same variant updates the existing line instead of adding a duplicate; setting a variant's quantity to 0 removes it and forgets it; and removing a variant that was never added is a safe no-op rather than an error. Twelve assertions across five scenarios, all passing.

Acceptance checklist

  • Adding a first item creates exactly one cart; adding a second item reuses it
  • "Actually, make it 3" updates the existing line's quantity instead of adding a duplicate
  • "Never mind, remove that" takes the item out of the cart and the checkout link reflects it
  • The model's replies never contain a raw Shopify cart or line ID
  • Two different shoppers' carts never merge or leak into each other
5.4 · Lab

Order Placement Flow

Since payment happens on Shopify's own hosted checkout page, not inside the conversation, the agent confirms an order actually completed by looking it up via the Admin API afterward rather than assuming success.

⏱️

Real-time vs. after-the-fact

Handing over a checkoutUrl doesn't tell you what happens next — the shopper might pay immediately, abandon it, or come back an hour later. This lab covers the simplest reliable pattern: when a shopper asks something like "did my order go through?", look it up by the email they give you. Module 6's event-driven agent later adds the other half — reacting the moment Lab 3.8's webhook fires, instead of waiting to be asked.

Try prompting Claude Code with something like:

"Add a third, read-only tool so the agent can answer 'did my order go through?' after the fact, since it can never know that synchronously. Write tools/checkOrderStatus.js: a tool called check_order_status taking a shopper's email, that queries the Admin API's orders field filtered by that email (query: 'email:<address>'), sorted by CREATED_AT descending, and returns each order's name, financial status, and fulfillment status. Reuse the same Admin client-credentials helper from Lab 3.6 for the request - this just needs the read_orders scope added to that same Dev Dashboard app, not a new one. Make sure the agent asks for an email if it doesn't have one yet rather than guessing, and that it never claims an order succeeded without having actually called this tool."
⚠️ Verify the field names against your own store first, before trusting Claude Code's output as-is. displayFinancialStatus and displayFulfillmentStatus are the fields this tool is written against, but Admin API schemas do shift between versions. Run the exact query in the GraphiQL app from Lab 3.3 against your dev store first — the same "test it live before trusting it" habit every Admin API query in this program has needed so far.

Acceptance checklist

  • Asking about an order with no email yet prompts the agent to ask for one, rather than guessing
  • A real completed order's financial and fulfillment status come back accurately
  • An email with no orders gets a clear "nothing found" answer, not an error or a hallucinated order
  • The tool never claims an order succeeded without having actually queried for it
5.5 · Lab

Multi-Item & Edge-Case Conversations

No new architecture here — this lab stress-tests the agent you've already built against the conversational situations that actually come up, and closes the two real gaps that surface when you do.

📦

Out-of-stock, before the cart mutation ever runs

Add availableForSale to search_products' query and its output schema. When a shopper tries to add something that's out of stock, the agent should say so using data it already has — not find out from a failed cartLinesAdd call.

🏷️

Discount codes are a cart mutation too

A fourth tool, apply_discount_code, wraps the Storefront API's cartDiscountCodesUpdate mutation against this session's tracked cartId — no new state to manage, since Topic 5.3 already keeps the cart ID out of the model's hands.

Try prompting Claude Code with something like:

"Extend the two existing tools to close two real gaps. First, add availableForSale to search_products' GraphQL query and its output schema, so every search result already says whether an item is in stock. The agent should mention this directly in its own reply rather than letting a shopper find out only when update_cart fails. Second, add a fourth tool, apply_discount_code, that takes a discount code and calls the Storefront API's cartDiscountCodesUpdate mutation against this session's already-tracked cartId - no new state to manage, since update_cart's cart manager from Topic 5.3 already keeps it. Return the resulting checkoutUrl so the shopper can see the discount reflected."
What "handling" out-of-stock means here: the agent should never silently add an unavailable item and let Shopify's checkout be the one to break the news. It should say so in the same reply as the search result, using availableForSale it already fetched.

Work through this conversation end to end, watching which tool fires at each step:

  • "Do you have any wireless headphones?" — search_products, includes stock status for each result
  • "Add two of the black ones" — update_cart creates the cart
  • "Actually, just one" — update_cart again, same variant, quantity corrected in place
  • "Do you have the white ones too? Add one" — a second line added to the same cart
  • "I have a code, SAVE10" — apply_discount_code, checkout link reflects the discount
  • "Never mind the white ones, remove them" — that line removed, the black-headphone line untouched

Acceptance checklist

  • An out-of-stock item is flagged in the agent's own reply, not discovered later at checkout
  • A quantity correction updates the existing line rather than creating a second one for the same item
  • A valid discount code changes the checkout link's total; an invalid one is reported as invalid, not silently ignored
  • Removing one line item never disturbs any other line in the same cart
  • The full six-step conversation above completes without the agent losing track of the cart
5.6 · Demo

Wiring It Into a React Chat Widget

Live demo connecting the React chat widget to the Node.js agent backend and embedding it on the dev store storefront — an end-to-end walkthrough of ask → browse → cart → pay → confirm, using everything built in this module.

🪪

One browser, one session ID

The widget generates a random ID on first load, stores it in localStorage, and sends it with every request — that's the only thing connecting a browser tab to a specific ChatSession and cart on the backend from Topics 5.2–5.3. No login is required for any of this.

Try prompting Claude Code with something like:

"Build ChatWidget.jsx, a React component for the storefront chat window. On first render, generate a random UUID as this browser's session ID and persist it in localStorage under a fixed key, reusing it on every later visit rather than generating a new one each time - that ID is the only thing connecting this browser tab to a specific ChatSession and cart on the backend. Hold a list of messages and an input value in state. On submit, append the shopper's message to the list immediately, POST { sessionId, message } to /api/chat, and append the agent's reply once it comes back - showing a lightweight typing indicator while waiting, and a graceful error message if the request fails rather than leaving the shopper staring at nothing. Auto-scroll to the latest message whenever the list changes."
Syntax-verified before this page was written: the resulting component was bundled with esbuild's JSX transform to confirm it compiles cleanly — the logic itself is exercised indirectly through Topics 5.2–5.5's tested backend, since the widget is a thin fetch-and-render layer on top of it.

Embedding on the storefront itself is a build-and-drop step: bundle this component, mount it into a small script your theme loads on every page (a theme app extension, or simply a <script> tag pointing at the built bundle), and point apiUrl at your deployed backend. The demo walks through that handoff live, end to end, on the dev store.
